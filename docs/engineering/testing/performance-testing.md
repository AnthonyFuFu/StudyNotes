# 效能測試與壓測

!!! abstract "本章重點"

    功能測試確認「對不對」，效能測試確認「撐不撐得住」。本章說明負載、壓力、尖峰、浸泡四種測試的目的，要看哪些指標，比較 JMeter、k6、Gatling，並以 holidayDessert 的搶票壓測工具說明如何設計可重複的壓測。

## 四種效能測試

``` mermaid
flowchart LR
    L["負載測試<br>預期流量下是否正常"] --> S["壓力測試<br>逐步加壓找極限"] --> SP["尖峰測試<br>瞬間暴增流量"] --> SO["浸泡測試<br>長時間運行"]
```

| 類型 | 目的 | 能發現的問題 |
|------|------|-------------|
| **負載測試**（Load） | 預期流量下，延遲與錯誤率是否符合 SLO | 一般效能瓶頸 |
| **壓力測試**（Stress） | 逐步加壓，找出系統的極限與崩潰點 | 最大容量、崩潰時的行為 |
| **尖峰測試**（Spike） | 瞬間湧入大量請求 | 自動擴展來不及、連線池耗盡（例如搶票開賣） |
| **浸泡測試**（Soak） | 長時間（數小時）維持負載 | **記憶體洩漏**、連線未釋放、日誌塞滿磁碟 |

## 要看哪些指標

| 指標 | 意義 | 為什麼重要 |
|------|------|-----------|
| **TPS / QPS** | 每秒完成的交易 / 請求數 | 系統的吞吐量 |
| **P95 / P99 延遲** | 95% / 99% 的請求在多少時間內完成 | **平均值會掩蓋長尾**，P99 才是最慢那群使用者的體驗 |
| **錯誤率** | 失敗請求的比例 | 吞吐量再高，錯誤率上升就是撐不住了 |
| **資源使用率** | CPU、記憶體、GC、連線池、DB 連線 | 找出真正的瓶頸在哪一層 |

!!! tip "Little's Law：估算需要多少並發"

    **並發數 = 吞吐量 × 平均回應時間**。目標 1,000 TPS、平均回應 200ms，系統中同時就有約 1000 × 0.2 = **200 個請求**在處理。這可以用來估算執行緒池、連線池要開多大。

## 工具比較

| | JMeter | k6 | Gatling |
|---|--------|-----|---------|
| 腳本 | GUI / XML | **JavaScript** | Scala / Java DSL |
| 資源用量 | 高（每個虛擬使用者一條執行緒） | 低（Go 實作） | 低（非同步） |
| CI 整合 | 可以，較笨重 | ✅ 非常容易 | ✅ 容易 |
| 報表 | 外掛 | 終端摘要 + Grafana | ✅ 內建漂亮的 HTML 報表 |
| 適合 | 協定多樣、非開發人員操作 | 開發團隊、寫成程式碼放進版控 | Java 團隊 |

=== "k6 範例"

    ``` javascript
    import http from 'k6/http';
    import { check } from 'k6';

    export const options = {
      stages: [
        { duration: '30s', target: 200 },    // 30 秒內爬升到 200 個虛擬使用者
        { duration: '1m',  target: 200 },    // 維持 1 分鐘
        { duration: '10s', target: 2000 },   // 模擬開賣尖峰
        { duration: '30s', target: 0 },
      ],
      thresholds: {
        http_req_duration: ['p(99)<800'],    // P99 < 800ms，否則判定失敗
        http_req_failed:   ['rate<0.01'],    // 錯誤率 < 1%
      },
    };

    export default function () {
      const res = http.post('http://localhost:8080/holidayDessert/api/tickets/purchase',
        JSON.stringify({ typeId: 1, quantity: 2 }),
        { headers: { 'Content-Type': 'application/json', Authorization: `Bearer ${__ENV.TOKEN}` } });
      check(res, { 'status is 200': (r) => r.status === 200 });
    }
    ```

=== "JMeter 重點"

    - **Thread Group**：虛擬使用者數、爬升時間、迴圈次數
    - **CSV Data Set Config**：每個虛擬使用者讀不同的帳號，避免全部打同一筆資料
    - **Assertions**：檢查回應碼與內容，不然錯誤回應也會被算成成功
    - 正式壓測用 **CLI 模式**（`jmeter -n -t plan.jmx -l result.jtl`），GUI 只用來編輯腳本

## 我的實作：搶票壓測工具

!!! abstract "專案：holidayDessert"

    後台內建「搶票模擬」：一鍵模擬最多 **2,000 名會員**同時搶票，回報成功、售罄、超過上限、系統繁忙各有多少人，以及售出張數、耗時與 TPS；也可以一鍵**重置活動**（刪訂單 → 還原庫存 → 清 Redis → 重新預熱），讓每次壓測都從相同的狀態開始。

| 設計 | 原因 |
|------|------|
| 結果依類型分類統計 | 只看成功率不夠，要知道是「售罄」還是「系統繁忙」才知道瓶頸在哪 |
| 驗證**售出張數 = 原始庫存 - 剩餘** | 高併發測試最重要的是**不超賣**，不是速度 |
| 一鍵重置 | 壓測必須可重複，否則前後兩次結果無法比較 |
| 回報 TPS 與耗時 | 調整 Semaphore 許可數、執行緒池大小後，可以直接比較效果 |

## 壓測的注意事項

- ✅ **用接近正式環境的資料量與機器規格**，在空資料庫上的結果沒有參考價值
- ✅ 壓測機與被測系統分開，避免壓測工具本身吃掉資源
- ✅ 同時觀察 [Prometheus / Grafana](../monitoring/prometheus.md)，把延遲曲線和 CPU、GC、連線池對照，才找得到瓶頸
- ✅ 先預熱（JIT 編譯、快取載入）再開始記錄
- ❌ 不要在正式環境壓測，除非有完整的隔離與流量標記
- ❌ 不要只看平均延遲
