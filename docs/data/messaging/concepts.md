# 核心概念：為什麼需要訊息佇列

!!! abstract "本章重點"

    訊息佇列解決削峰填谷、非同步處理與服務解耦三個問題，同時也帶來一致性與重複訊息的代價。本章說明三種投遞語意、「至少一次 + 冪等消費」的標準做法，以及如何確保訊息不遺失。

## 三個典型用途

=== "削峰填谷"

    ``` mermaid
    flowchart LR
        U(["瞬間 2,000 筆搶票成功"]) --> MQ[("訊息佇列")] -- "依資料庫能力<br>穩定消費" --> DB[("MySQL")]
    ```

    流量尖峰先進佇列緩衝，下游依自己的速度處理。holidayDessert 搶票訂單就是這樣寫入資料庫的。

=== "非同步處理"

    ``` mermaid
    flowchart LR
        A["註冊會員"] --> R(["立即回應成功"])
        A -.-> MQ[("訊息佇列")] -.-> M["寄驗證信"] & S["統計"] & P["發優惠券"]
    ```

    主流程只做必要的事，其他工作丟給佇列，回應時間大幅縮短。

=== "服務解耦"

    ``` mermaid
    flowchart LR
        PV["會員服務"] -- "發布：會員已建立" --> MQ[("訊息佇列")]
        MQ --> C1["通知服務"]
        MQ --> C2["點數服務"]
    ```

    發送方不需要知道誰會處理事件，新增消費者也不用改發送方。microservicecloud 的會員事件就是這樣設計的。

## 代價

| 引入 MQ 之後 | 要處理的問題 |
|-------------|-------------|
| 多一個元件 | MQ 本身要高可用（叢集、副本） |
| 非同步 | 使用者看到成功時，資料可能還沒寫入（**最終一致性**） |
| 網路不可靠 | 訊息可能**遺失**或**重複** |
| 多消費者 | 訊息**順序**可能被打亂 |

## 投遞語意

| 語意 | 意義 | 怎麼做到 | 風險 |
|------|------|---------|------|
| **At most once** | 最多一次 | 先確認（ack）再處理 | 處理失敗就遺失 |
| **At least once**（最常用） | 至少一次 | 先處理再確認 | **可能重複** |
| **Exactly once** | 剛好一次 | Kafka 交易 + 冪等 Producer，或消費端冪等 | 成本高、限制多 |

!!! tip "實務上的標準解法：At least once + 冪等消費"

    讓訊息「可能重複」，但消費端處理同一筆訊息多次的結果與一次相同：

    - 訊息帶唯一 ID，處理前檢查 Redis `SETNX` 或資料庫唯一索引
    - 用條件式 UPDATE（`WHERE status = 'PENDING'`），重複執行不會有副作用
    - 用 UPSERT 取代 INSERT

## 訊息不遺失的三個環節

``` mermaid
flowchart LR
    P["Producer"] -- "① 發送確認" --> B[("Broker")] -- "③ 消費確認" --> C["Consumer"]
    B -- "② 持久化 + 副本" --> D[("磁碟")]
```

| 環節 | Kafka | RabbitMQ |
|------|-------|----------|
| ① 發送 | `acks=all` + 重試 | Publisher Confirms |
| ② 儲存 | Topic 副本數 ≥ 3、`min.insync.replicas=2` | 持久化佇列 + 持久化訊息 + Quorum Queue |
| ③ 消費 | 處理完才提交 offset | 手動 ack，處理完才確認 |

## 怎麼選

| 情境 | 建議 |
|------|------|
| 大量事件、日誌、需要**重播**歷史資料、串流處理 | **Kafka** |
| 業務訊息、需要**彈性路由**、延遲 / 優先權佇列、低延遲 | **RabbitMQ** |
| 只是單機內非同步 | `@Async` 執行緒池就好，不需要 MQ |
